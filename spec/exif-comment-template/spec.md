# Feature Specification: EXIF 备注模板自定义

**Created**: 2026-07-19
**Updated**: 2026-07-23（第三轮：EXIF+XMP 双写策略）
**Status**: Draft
**Input**: User description: "备注内容要做成和文件名称一样可以在设置里面自定义"；修复："修复图片备注信息在比较长的情况下写入失败的问题"；追加："不是所有的照片都写入失败，应该是先判断下载的图片是否有exif，再处理"；"同时在xmp上写入相关数据，用于覆盖png等格式无法写入exif的问题"；"JPEG 图片 Exif + XMP 双重写入确保最大兼容性，PNG等图片 XMP 写入"

## Overview

当前下载图片写入 EXIF 备注（UserComment）的内容是硬编码格式，用户无法自定义。本功能将备注内容改为模板化配置，与现有的文件名模板功能一致：用户在设置中编辑模板、插入变量、实时预览，下载图片时按模板渲染备注并写入 EXIF。模板变量在文件名模板变量基础上，额外提供独立的 `{tags}`（仅原文标签）和 `{tags_translated}`（带翻译标签）两个标签变量。

**修复（2026-07-23，设备实证根因）**：部分图片备注写入失败的根因是 HarmonyOS `modifyImageProperty` 仅支持**已包含 EXIF 信息**的图片，而 Pixiv 部分图片 EXIF 段被剥离（有 EXIF 的图可写入成功）。修复目标——按格式分流的双重写入策略：

1. **JPEG 图片：EXIF + XMP 双重写入**，确保最大兼容性——
   - 下载后先探测源图是否包含 EXIF；
   - 有 EXIF → 走系统 API 写入 EXIF（超长时先完整写入、失败后逐级截断重试）；
   - 无 EXIF → 手工构造 EXIF 段注入原始字节流（不重编码、画质无损）；
   - 无论有无 EXIF，同时写入 XMP 元数据作为第二载体；
2. **PNG 等无法写入 EXIF 的格式：XMP 写入**，携带同等元数据；
3. 任何路径失败均不阻断下载——降级保存原始图片，下载任务仍标记成功；双写场景下任一载体失败不影响另一载体的写入尝试。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自定义备注模板并生效于下载图片 (Priority: P1)

用户在设置中打开备注模板编辑页，修改模板（例如改为 `{title} {tags_translated}`），保存后下载一张插画。保存到图库后，该图片的备注内容按照用户配置的模板渲染显示。

**Why this priority**: 这是本功能的核心价值——备注内容可由用户控制。

**Independent Test**: 可通过「修改模板 → 下载图片 → 查看图库备注」的完整链路独立验证。

**Acceptance Scenarios**:

1. **Given** 用户已将备注模板设置为 `PID:{illust_id} | {tags}`，**When** 下载一张带标签的插画并保存到图库，**Then** 图库中该图片备注显示为 `PID:12345678 | 标签1, 标签2, ...` 的形式。
2. **Given** 用户已将模板设置为 `{title} by {user_name}`，**When** 下载插画并保存到图库，**Then** 备注显示为「标题 by 作者名」，不包含未替换的 `{...}` 占位符。
3. **Given** 用户的模板渲染结果超长（如标题+20 个以上带翻译标签），**When** 下载插画，**Then** 备注先尝试完整写入，失败后逐级截断重试直至成功，下载任务正常完成，图库备注显示截断后的内容（以 `...` 结尾，不切断多字节字符）。

---

### User Story 2 - 写入失败时下载不中断 (Priority: P1)

用户下载一张元数据写入全部失败的插画。下载任务不会失败：应用降级保存原始图片文件，下载记录标记为成功，用户能正常查看图片（仅缺失备注）。

**Why this priority**: 元数据是附加价值，不应凌驾于下载主流程之上；写入失败阻断下载属于可用性缺陷。

**Independent Test**: 下载一张无法写入任何元数据的图片，观察：图片文件存在且可打开，下载记录为成功。

**Acceptance Scenarios**:

1. **Given** 一张元数据写入全部失败的作品，**When** 下载该作品，**Then** 下载任务最终标记为成功，图片文件完整保存到下载目录。
2. **Given** JPEG 双写场景中 EXIF 写入失败但 XMP 成功（或反之），**When** 下载完成，**Then** 成功的载体数据保留在文件中，下载任务标记成功。
3. **Given** 嵌入流程中发生任何异常，**When** 下载流程继续，**Then** 不产生未处理异常导致应用崩溃，下载状态正确落库。

---

### User Story 3 - JPEG 双写：无 EXIF 的图也能写入备注 (Priority: P1)

用户下载一张源图不含 EXIF 段的 JPEG 作品（Pixiv 常见）。应用检测到源图无 EXIF 后，向原始字节流注入手工构造的 EXIF 段，同时写入 XMP 元数据；保存到图库后备注正常显示，且图片画质与原图一致（不重编码）。

**Why this priority**: 这是本轮修复的核心场景——设备实证确认无 EXIF 的 JPEG 通过系统接口写入必然失败；EXIF+XMP 双写确保任一元数据读取方都能获取备注。

**Independent Test**: 下载一张确认无 EXIF 的 JPEG 作品（如问题图 146416153_p0），保存到图库后查看备注：显示模板渲染内容；文件内同时存在 EXIF 段与 XMP 块；图片像素与原图一致（未被重编码压缩）。

**Acceptance Scenarios**:

1. **Given** 源图为无 EXIF 的 JPEG，**When** 下载并保存到图库，**Then** 图库备注显示模板渲染的完整内容（标题、标签等）。
2. **Given** 源图为无 EXIF 的 JPEG，**When** 检查下载文件，**Then** 文件内同时包含 EXIF 段与 XMP 元数据，且除注入的元数据外字节内容与原图一致（未经重编码）。
3. **Given** 源图含 EXIF，**When** 下载，**Then** 系统接口写入路径生效，源图既有 EXIF 信息不丢失，且 XMP 元数据同步写入。

---

### User Story 4 - PNG 等格式通过 XMP 写入备注 (Priority: P2)

用户下载一张 PNG（或其他无法写入 EXIF 的格式）作品。应用将同一份模板渲染的元数据以 XMP 形式写入图片文件，使这类格式也能携带备注信息；保存到图库后，支持 XMP 的查看器可读取到该信息。

**Why this priority**: PNG 在 Pixiv 占相当比例；XMP 是跨格式的通用元数据标准。优先级低于 JPEG 主线修复（图库是否展示 XMP 备注取决于系统实现，价值存在不确定性）。

**Independent Test**: 下载一张 PNG 作品，验证文件内包含 XMP 元数据块且内容符合模板渲染结果；下载任务标记成功。

**Acceptance Scenarios**:

1. **Given** 源图为 PNG，**When** 下载完成，**Then** 图片文件内包含 XMP 元数据，其中备注相关字段内容与模板渲染结果一致。
2. **Given** 源图为 PNG，**When** XMP 写入成功，**Then** 图片像素数据未被改动（文件仍可作为正常 PNG 打开显示）。
3. **Given** XMP 写入失败，**When** 下载流程继续，**Then** 降级保存原始图片，下载任务标记成功。

---

### User Story 5 - 在编辑页插入变量并实时预览 (Priority: P2)

用户在备注模板编辑页，通过点击变量按钮将变量插入模板文本，页面实时显示使用示例数据渲染后的备注预览效果，并展示各变量的含义说明。

**Why this priority**: 与文件名模板页一致的编辑体验降低学习成本。

**Independent Test**: 可独立测试编辑页的交互——插入变量、编辑文本、预览刷新，无需触发真实下载。

**Acceptance Scenarios**:

1. **Given** 用户位于备注模板编辑页，**When** 点击 `{tags}` 变量按钮，**Then** 模板输入框末尾追加 `{tags}`，预览区域同步刷新为示例渲染结果。
2. **Given** 用户将模板清空，**When** 点击保存，**Then** 模板恢复为默认值 `PID:{illust_id} | {tags}` 并保存成功。

---

### User Story 6 - 标签翻译变量的独立控制 (Priority: P3)

用户在模板中分别使用 `{tags}`（仅原文标签）和 `{tags_translated}`（带翻译标签），下载图片后备注按所选变量形式渲染标签内容。

**Why this priority**: 用户对标签显示形式有不同偏好，提供两个独立变量更灵活。

**Independent Test**: 可分别配置含 `{tags}` 和 `{tags_translated}` 的模板并下载验证。

**Acceptance Scenarios**:

1. **Given** 模板包含 `{tags}`，**When** 下载带翻译标签的插画，**Then** 备注中标签仅显示原文，不含括号翻译。
2. **Given** 模板包含 `{tags_translated}`，**When** 下载带翻译标签的插画，**Then** 备注中标签显示为「原文 (翻译)」形式；无翻译的标签仅显示原文。

---

### Edge Cases

- 模板为空或全为空白字符时，保存自动回退为默认值 `PID:{illust_id} | {tags}`。
- 模板中包含未定义的 `{xxx}` 占位符时，该占位符按原样保留输出（不报错）。
- 作品无标签时，`{tags}` / `{tags_translated}` 渲染为空字符串。
- JPEG 有 EXIF 时：渲染结果先尝试完整写入，失败后按 UTF-8 字节数逐级截断（不切断多字节字符）并附加 `...` 重试，直至成功或达到保底长度放弃该字段；XMP 写入不受影响。
- JPEG 无 EXIF 时：注入手工构造的 EXIF 段 + 写入 XMP；段容量（约 64KB）远高于实际渲染长度，触顶时按 UTF-8 字节安全截断 UserComment。
- PNG 等无法写 EXIF 的格式：仅写入 XMP；XMP 失败则降级保存原图，下载成功。
- JPEG 双写中某一载体失败：另一载体照常尝试，互不影响；两者均失败才走降级。
- 源图 EXIF 段损坏或探测返回非预期异常时：按"无 EXIF"分支处理并记日志；仍失败则降级。
- 「写入图片元数据」开关关闭时，不写入任何元数据，模板配置不生效（但配置本身仍保留）。
- GIF 维持不嵌入任何元数据的既有行为。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供「EXIF 备注模板」设置项，持久化存储，默认值为 `PID:{illust_id} | {tags}`。
- **FR-002**: 系统 MUST 在设置页提供备注模板编辑入口，编辑体验与文件名模板页一致（文本输入、变量插入按钮、实时预览、变量说明）。
- **FR-003**: 备注模板 MUST 支持变量：`{illust_id}`、`{user_id}`、`{user_name}`、`{title}`、`{part}`、`{tags}`（仅原文）、`{tags_translated}`（带翻译，无翻译时仅原文）。
- **FR-004**: 下载图片写入元数据时，系统 MUST 按当前模板渲染备注内容，且 EXIF 与 XMP 使用同一份渲染结果。
- **FR-005**: JPEG 图片 MUST 双重写入 EXIF 与 XMP 元数据以确保最大兼容性：先探测源图是否包含 EXIF——有 EXIF 时走系统写入接口写入 EXIF，无 EXIF 时注入手工构造的 EXIF 段；无论有无 EXIF，同时写入 XMP 元数据。两个载体的写入 MUST 相互独立，任一失败不影响另一载体的尝试。
- **FR-006**: 系统接口写入备注时 MUST 先尝试完整渲染结果；写入失败时按 UTF-8 字节数逐级截断（不切断多字节字符，截断后附加 `...`）并重试，直至成功或达到保底长度。系统 MUST NOT 依赖预设的固定字节上限假设来决定首次写入内容。
- **FR-007**: 无 EXIF 的 JPEG 注入元数据段时 MUST NOT 重编码图片：输出 = 原始字节流 + 注入的元数据段，画质与原图一致。
- **FR-008**: 未定义的 `{xxx}` 占位符 MUST 按原样保留，不得导致渲染失败或下载失败。
- **FR-009**: 元数据嵌入流程任何失败（含双写均失败、格式不支持、文件操作异常等）MUST NOT 阻断下载主流程：系统 MUST 降级为直接保存原始下载图片，下载任务 MUST 标记为成功，下载记录中的文件路径 MUST 指向可用的图片文件。
- **FR-010**: 元数据嵌入降级时，系统 MUST 清理临时文件，不得在下载目录残留未使用的中间文件。
- **FR-011**: 写入失败的降级过程 MUST 记录日志（含失败的载体、字段与降级原因），便于问题排查；日志不产生用户可见的报错打扰。
- **FR-012**: 对无法写入 EXIF 的格式（PNG 等），系统 MUST 以 XMP 形式写入元数据，XMP 中的备注相关字段内容 MUST 与模板渲染结果一致（同一渲染输出，不做差异化裁剪）；写入过程 MUST NOT 破坏图片像素数据（文件仍可正常打开显示）。
- **FR-013**: XMP 写入失败 MUST 走与 EXIF 失败一致的降级路径（保存原图、下载成功、清理临时文件、记日志）。
- **FR-014**: 模板为空或全空白时保存，系统 MUST 自动回退为默认值。升级后已有用户的备注行为 MUST 与当前版本默认行为兼容。

### Key Entities

- **备注模板（ExifCommentTemplate）**: 字符串设置项，含 `{...}` 变量占位符；默认 `PID:{illust_id} | {tags}`；通过偏好存储持久化。
- **模板变量（TemplateVariable）**: `{illust_id}`、`{user_id}`、`{user_name}`、`{title}`、`{part}`、`{tags}`、`{tags_translated}`，渲染时从当前下载的插画数据取值。
- **元数据载体（MetadataCarrier）**: JPEG → EXIF（系统接口或手工注入段）+ XMP 双写；PNG 等 → XMP；同一份模板渲染结果写入各载体。
- **嵌入结果（EmbedOutcome）**: 成功（至少一个载体写入成功，含截断后成功）或降级保存原图（全部载体失败）；仅影响图片元数据，不影响下载任务的成功状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可在 30 秒内完成一次备注模板修改并保存。
- **SC-002**: 配置模板后下载的图片，其备注 100% 按模板渲染显示（变量全部替换为实际值，无残留 `{...}` 已知占位符）。
- **SC-003**: 含 20+ 个中日混合长标签的作品下载成功率与短标签作品一致（100%），不因备注长度导致下载失败。
- **SC-004**: JPEG 作品下载后，文件内同时存在 EXIF 与 XMP 双份元数据（写入路径未失败时），图库备注 100% 可见。
- **SC-005**: 无 EXIF 的 JPEG 注入元数据后，图片画质与原图 100% 一致（无重编码）。
- **SC-006**: PNG 作品下载后，文件内 100% 包含与模板渲染结果一致的 XMP 元数据（写入路径未失败时）。
- **SC-007**: 模板编辑页预览与实际下载结果的渲染规则完全一致。
- **SC-008**: 元数据写入彻底失败的极端情况下，图片文件 100% 仍可正常打开浏览，下载记录状态为成功。

## Assumptions

- 仅备注内容支持模板自定义；ImageDescription、Artist、Copyright 等字段维持现有硬编码逻辑；XMP 写入的字段集合与 EXIF 保持一致。
- `{tags}` / `{tags_translated}` 的标签拼接分隔符固定为 `, `（与现有逻辑一致）。
- 标签翻译显示遵循现有 `translatedName` 数据：有翻译且与原文不同则显示为「原文 (翻译)」，否则仅原文。
- EXIF 各字段经系统接口写入的实际容量以设备运行时行为为准，不做固定字节数预设；截断按 UTF-8 字节数计算，保底长度约为 50 字节。
- UserComment 采用 `ASCII\0\0\0` 字符集前缀 + UTF-8 字节（业界事实标准）；图库对 XMP 备注的展示能力取决于系统实现，XMP 以保证"数据写入文件"为验收标准。
- 降级保存原图时保持原图格式与画质。
- 本功能不改变 GIF 不嵌入元数据的现有行为。

## Open Questions

- 无（双写策略、XMP 覆盖范围、失败降级行为均已确认）。
